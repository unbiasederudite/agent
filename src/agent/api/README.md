# api

Inbound HTTP adapter. Thin translation layer between HTTP and `core/services/` — contains no reasoning of its own.

## Contents

- `schemas.py` — backend-native request/response models. `AgentRunRequest`/`AgentRunResponse` model `POST /v1/agents/{agent_name}` (`message` as a plain string, optional `model`/`strategy`/`temperature`/`top_p`/`max_tokens` overrides, tri-state `tools`: omitted uses the agent's tools, `[]` suppresses them, a list overrides them; optional `session_id` continues an existing conversation, omitted starts a new one). `AgentRunRequest` sets `model_config = ConfigDict(extra="forbid")`: an unrecognized field in the request body (e.g. a typo'd key) raises a 400 validation error instead of being silently ignored. `temperature`/`max_tokens` only enforce a universal lower bound (`ge=0`/`ge=1`) here, not a provider-specific upper bound (e.g. OpenAI's 2, Anthropic's 1 for `temperature`) -- an out-of-range value is left for the provider itself to reject, matching how `model`/`strategy`/`tools`/`session_id` are all validated downstream against a registry rather than at the schema layer. Tool calls requested by the LLM are executed server-side and fed back automatically (up to `AgentConfig.max_tool_iterations`). The response `message`/`usage` reuse `core.models.message.Message` and `core.models.usage.Usage` directly rather than duplicating identical DTOs — `models` is cross-cutting per `ARCHITECTURE.md`, so there's nothing to translate for those. `AgentRunResponse` stays its own model rather than reusing `core.models.run.Run` directly, keeping the API-facing DTO independent of the internal domain model. `AgentSummary`/`ToolSummary` model the `GET /v1/agents`/`GET /v1/tools` listing entries — deliberately reduced projections (`AgentSummary` omits `AgentConfig.system_prompt` and sampling defaults) rather than reusing the core models, since exposing those isn't safe.
- `app.py` — `create_app(config_path)` builds the FastAPI app from an `AppConfig` JSON file: reads and parses `config_path` itself (`ConfigError` on a missing file or invalid JSON) before calling `build_registries()` with the parsed `AppConfig` -- reading/parsing the file is I/O, which `core/factories/` (like the rest of `core/`) owns none of. Passes the returned `LoggingConfig` to `configure_logging()` (with a `RequestIdFilter` and a `RunContextFilter` attached), wires `RequestIdMiddleware` via `app.add_middleware()`, and constructs a `CompactionService` when the config declares one. Logs one INFO line at startup with wiring counts (agent/tool/LLM/strategy counts, whether compaction is enabled). `add_agent_run_route()` registers `POST /v1/agents/{agent_name}`. Ten exception types map to a uniform `{"message": str(exc), "code": ...}` shape with no custom message or headers -- these are looked up in `_UNIFORM_ERROR_MAP` (a `{exception type: (status, code)}` table) and handled by one shared `except tuple(_UNIFORM_ERROR_MAP) as exc` clause instead of ten near-identical ones; safe because none of the ten subclass each other or anything handled separately, so the caught instance's exact type is always a valid table key. Everything else keeps its own `except` clause for a custom message/headers/logging: `InputTooLargeError` and `LLMContextWindowExceededError`/`CompactionExhaustedError` map to 413 (RFC 9110 section 15.5.14 -- content too large for the server/model to process, not a generic 400 or an *invalid* upstream response, which is what 502 means per section 15.6.3), `LLMOverloadedError` to 503; error messages are human-authored (never the raw `str(exc)`) so internal detail never leaks to clients. `CompactionExhaustedError` (a subclass of `LLMContextWindowExceededError`) and `LLMOverloadedError` (a subclass of `LLMError`) are each checked *before* their broader parent's `except` clause -- `except` clauses run in order, and the more specific subclass must come first or its handler is unreachable. `add_registry_routes()` registers `GET /v1/agents`, `GET /v1/tools`, `GET /v1/models`, `GET /v1/strategies`, each logging a DEBUG line with its result count. `add_health_route()` registers `GET /health`, a liveness check only (no provider pings, not logged). `add_session_routes()` registers `GET`/`DELETE /v1/agents/{agent_name}/sessions/{session_id}`, both pure translation over a `SessionService` (`core/services/session_service.py`) built in `create_app()`: `GET` calls `get_history()` (404 `session_not_found` if unknown); `DELETE` calls `delete()` (409 `session_busy` if another operation already holds the session) and returns `204` on success -- the busy-guard-plus-delete-plus-forget-compaction-estimate sequencing itself lives in `SessionService`, not here, so it isn't reimplemented by a future `cli/` inbound adapter. `_UNIFORM_ERROR_MAP` also covers `SessionBusyError` (`409 session_busy`) and `ToolNotAllowedError`/`ModelNotAllowedError`/`StrategyNotAllowedError` (`403 tool_not_allowed`/`model_not_allowed`/`strategy_not_allowed`). `RequestTimeoutError` maps to `504` (distinct from the existing `504` `LLMTimeoutError` mapping -- neither carries a `code`, so the two are distinguished by message text); the `429`/`503` mappings (`LLMRateLimitedError`/`LLMOverloadedError`) additionally set a `Retry-After` header (a fixed conservative value -- litellm doesn't surface a provider-supplied one to forward). `add_exception_handlers()` registers a 400 handler for request-validation failures, one shared `StarletteHTTPException` handler covering every `HTTPException` in the app -- both framework-level 404/405s (Starlette's own default `detail` is a bare string) and every deliberately-raised one from `add_agent_run_route` (`{"message": ..., "code": ...}`-shaped) are normalized into the same `{"message": ...}` shape, `code` present only when added; logs one INFO line for 404/405, which have no log line anywhere upstream -- 413 (`InputTooLargeError`) already has one in `agent_run.py`, so it's deliberately excluded here to avoid double-logging the same event -- and a 500 catch-all. Note: once `RequestIdMiddleware` is wired in, the 500 catch-all in `add_exception_handlers()` is structurally unreachable for genuinely unhandled exceptions (Starlette's `ServerErrorMiddleware` sits outside every middleware added via `app.add_middleware()`) -- `RequestIdMiddleware`'s own fallback in `request_context.py` handles that case first, logging an ERROR with traceback before responding. See the root `README.md`'s Errors section for the full status/`code` table.
- `logging_setup.py` — `JsonFormatter` (renders `LogRecord`s as JSON with structured extra fields, including `request_id`/`agent`/`session_id` when set), `RunContextFilter` (stamps `record.agent`/`record.session_id` onto every `LogRecord` from `core.run_context.current_run_context()` -- both `None` outside an `AgentRunService.run()` call), and `configure_logging()` (wires console/file handlers, formatter selection, and every filter passed to it -- now variadic, `*extra_filters`, since two independent correlation filters are attached in practice) per `LoggingConfig`. Called once at startup, from `create_app()`, to configure process-level logging.
- `request_context.py` — `RequestIdMiddleware` (assigns/echoes an `X-Request-ID` per request via a `ContextVar`, and is the de facto handler for unhandled exceptions once wired into `create_app()` -- see note above). Pure ASGI (`__call__(scope, receive, send)`), not `@app.middleware("http")`/`BaseHTTPMiddleware` -- the latter runs the downstream app in a separate task, which doesn't reliably propagate `ContextVar` changes in every case (Starlette's own documented limitation); this app doesn't hit the specific cases that matter (no `BackgroundTasks`, no multipart bodies) but the pure-ASGI form has no such gap at all. A client-supplied `X-Request-ID` is only echoed back if it matches `_SAFE_REQUEST_ID` (`[A-Za-z0-9._-]`, 1-128 chars) -- otherwise treated as absent and a fresh id is generated, closing a log-injection path (a crafted header value flows unescaped into `"text"`-format log lines, `LoggingConfig`'s default format). `RequestIdFilter` (stamps `record.request_id` onto every `LogRecord` from the current request's id), `current_request_id()`.
- `__main__.py` — CLI entrypoint: parses `--config`/`--host`/`--port`, catches `ConfigError` at startup and exits with code 1 (printing a fatal message to stderr), then starts the server

## Running

    uv run python -m agent.api --config path/to/config.json

`--host` (default `127.0.0.1`) and `--port` (default `8000`) are optional.
