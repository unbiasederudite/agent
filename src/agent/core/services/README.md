# services

Use-case orchestration, called by inbound adapters.

## Contents

- `agent_run.py` — `AgentRunService`, resolves a required agent (and optional model/strategy/tools override) by name, rejects a `message` longer than the agent's configured `max_input_chars`, builds the initial system+user messages (merging the process-wide `base_prompt`, if configured, into the agent's `system_prompt`), resolves tool names against `ToolRegistry` into instances before the strategy ever runs, threads a session's stored history (via `ISessionStore`) between the system message and the new user turn when `session_id` is given -- proactively compacting it first via `CompactionService` if it's over budget -- and delegates to the selected `IStrategy` to run the reasoning loop, retrying once through a fresh compaction pass if the loop overflows the model's context window, to produce a `Run`. The retry always uses the configured `keep_recent_turns` -- never overridden, never forced to 0 -- so the turns it protects are never summarized away by this call under any circumstance; if the retry overflows again, the request fails rather than discarding more than configured to try to force a fit. The retry is triggered only by a real `LLMContextWindowExceededError`, never by an estimate; if compaction can't help (fails outright, or the retry overflows again) it raises `CompactionExhaustedError` (a subclass of `LLMContextWindowExceededError`, surfaced by the API as `502 compaction_exhausted`), which distinguishes "compaction was tried and could not help" from a plain overflow where compaction was never available to try (no `compaction_service`, no prior `session_id`)
- `compaction.py` — `CompactionService`, keeps a session's stored history under its configured `CompactionConfig` token budget: `record_usage` tracks each turn's ending size per `(agent, session_id)`; `maybe_compact` checks that lagged estimate against a model's `ILLM.max_input_tokens()` before the next turn starts and calls `compact` if over budget; `AgentRunService` also calls `compact` directly and reactively, after an `LLMContextWindowExceededError`, regardless of budget. Always uses the configured `CompactionConfig.keep_recent_turns` -- no caller may override it, so the turns it protects are never summarized away under any circumstance, including on a reactive retry. The summary is stored as its own synthetic turn -- a `role="user"` message holding the summary text, followed by a fixed `role="assistant"` acknowledgment -- prepended before whatever turns are kept, the same shape regardless of `keep_recent_turns` (including 0, where nothing follows it). This keeps the stored history starting on `role="user"` and never produces two consecutive same-role messages, since the acknowledgment always sits between the summary and whatever comes next -- including `AgentRunService`'s freshly appended `role="user"` message on the following call. The old portion is passed to the summarizer as-is, tool exchanges included: the summarizer call declares no `tools`, and Bedrock's Converse API specifically rejects toolUse/toolResult content blocks in a request with no `toolConfig` (the direct Anthropic API is more permissive here, so this is a Bedrock constraint rather than a blanket Anthropic one) -- but folding that content out is the `ILLM` implementation's contractual job, done automatically for every no-tools call in `LiteLLMAdapter.complete()`, so `compact` does no pre-processing of its own. The shape constraints it *does* own still hold on both the stored history and the summarizer request: Anthropic requires a leading `role="user"` message, and Anthropic-via-Bedrock rejects consecutive same-role messages. A transient summarizer failure (any `LLMError` other than an overflow, a truncated response, or empty content) is retried exactly once with the same input -- for the single pass, and independently for each chunked-fallback map/reduce call too. A summarizer *overflow* is never retried that way -- the same oversized input would fail identically -- and instead falls back to chunked map-reduce summarization: the old portion is split into groups of whole turns, `CompactionConfig.chunk_turns` turns per group (default 4, tunable to trade chunk size against summarizer-call count -- unrelated to `keep_recent_turns`, which is about turns kept verbatim), each summarized independently, then those summaries are summarized into one final summary. Single level only, no recursion: if a chunk fails (even after its own retry) or overflows, the whole chunked attempt fails. Never corrupts stored history: a summarizer failure surviving its retry, a failed chunked fallback, a truncated (`finish_reason == "length"`) summary, or an empty/whitespace-only summary returns `False` and leaves history untouched -- `replace()` is only ever called once a usable summary exists. One further failure case guards against succeeding while shrinking nothing: if the synthetic summary pair's combined content length is not strictly smaller than the old portion it would replace, `compact` returns `False` without calling `replace()` or clearing the usage estimate. This is the shape a session already compacted once falls into as soon as exactly `keep_recent_turns` new turns have accumulated -- the split then lands the *previous* summary turn alone in the old portion, and re-summarizing it re-adds the summary prefix and acknowledgment on top of near-zero information while the bulky recent turns go untouched. Message count can't detect it (both sides are two messages), so the check is on content length. That exact shape is also caught earlier, structurally and unconditionally: before resolving the summarizer at all, `compact` checks whether the old portion is precisely the two-message synthetic pair it generates itself (the fixed `[Summary of earlier conversation]` prefix on a `role="user"` message, followed by the fixed `role="assistant"` acknowledgment) and returns `False` immediately -- there is nothing new to fold in, so re-running the summarizer over its own prior output alone is treated as non-retriable rather than a worthwhile speculative attempt, even in the edge case where that pair is the *entire* history (e.g. a session configured with `keep_recent_turns=0`) and would otherwise be the only lever left. This covers both compaction re-triggering with no new turns since the last one and that all-summary-no-recent shape, at zero summarizer-call cost either way; real compaction resumes automatically once genuinely new content becomes part of the old portion again, since that no longer matches this shape. The content-length guard stays as the general safety net behind it, for any other reason a summary comes back no smaller than what it would replace
